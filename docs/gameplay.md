# 玩法说明

Living Desktop 的核心不是播放一组孤立动画，而是让角色在真实桌面构成的游戏空间中持续
生活。窗口提供地面、边缘和障碍，角色、道具与用户操作共同产生短回合玩法。

## 一、用户与角色互动

用户操作拥有最高优先级，角色必须即时回应：

- 左键拖动角色，可在屏幕内上下左右移动，也可以跨显示器；
- 松手时保留抛掷速度，角色进入空中、碰撞和落地流程；
- 右键菜单只展示常用动作和该角色的特色动作；
- “角色”菜单管理当前在场人物，可邀请其他角色入场或让当前角色离场；
- 用户操作可以中断闲逛和自动剧情，完成后角色再恢复自主活动。

## 二、角色自己的生活

没有用户操作时，角色仍会根据当前桌面状态行动：

- 在可行走区域散步、奔跑、停留和休息；
- 对前台应用、窗口变化和附近角色作出短反应；
- 坐到窗口边缘、攀爬、探头或跟随窗口移动；
- 根据角色人格选择问候、帮助、回避、调侃、争执或其他行为；
- 体力、受伤、恐惧等状态会影响当前选择和表现。

角色能力与角色倾向是两回事：素材和身体能力决定“能不能做”，人格、关系和当前状态
决定“更愿意做什么”。缺少专属动作时可以降级为通用动作，但不能把降级表现冒充成
该角色的完整特色素材。

## 三、多角色与剧情

多个角色共享同一个世界，而不是各自运行互不相干的动画。玩法可以表达：

- 相遇、打招呼、交谈、共同休息；
- 帮助、保护、递交或争夺道具；
- 敌对角色接近、处理途中阻挡并最终战斗；
- 角色进入或离开场景，剧情被用户或桌面事件中断；
- 驾驶员进入机甲、离开驾驶舱或与其他角色协作。

剧情规划只描述角色关系、目标、节点和分支，不输出具体跨窗口路径。移动、避障、推开、
跳过或临时应对由角色的快速行动脑在运行过程中决定。

一个剧情是否完成必须有可检查的结果。例如“敌对双方战斗”的成功条件不是模型说了
“开始战斗”，而是双方完成接近、阻挡处理和有效战斗动作，并把结果提交到共享世界。

## 四、道具和桌面环境

道具可以被拿起、放下、传递、占用或附着在角色和场景插槽上。窗口可以成为平台、目标
或视觉效果承载面。典型玩法包括：

- 喝茶、阅读、使用电脑或电话；
- 把道具交给另一名角色；
- 坐到窗口边缘、从窗口后探头；
- 在窗口表面表现裂痕、弹孔、冲击和烟雾；
- 根据窗口遮挡和角色位置调整行动。

窗口破坏只是 Living Desktop 的视觉表现，不会改动外部应用窗口或其中的数据。

## 五、角色动作

玩法使用稳定的语义动作，而不是依赖某个素材文件名。常见动作包括：

| 类别 | 示例 |
|---|---|
| 基础活动 | idle、walk、run、sit、sleep、stretch |
| 情绪表达 | greet、happy、surprised、annoyed、think |
| 社交互动 | talk、listen、nod、tease、give、receive |
| 场景动作 | enter_scene、exit_scene、perch_window、climb、peek |
| 战斗动作 | taunt、attack、defend、dodge、hit_react |

每个角色可以把同一语义演成不同动作。例如同样是“问候”，角色可以挥手、行礼、点头或
冷淡地看一眼。角色特色来自角色配置和专属素材，不应在玩法代码中写死人物名字。

## 六、大脑与降级

运行时采用慢决策与快速行动分离的方式：高层只决定目标和剧情节点，快速行动脑负责当前
动作、路线和障碍处理。任何模型都不能绕过共享世界直接移动角色或修改剧情结果。

系统提供逐级降级：

1. 本地模型可用时，根据角色和桌面上下文产生目标或短台词；
2. 模型不可用时，使用内置策略继续玩法；
3. 专属素材缺失时，使用合法的通用动作或几何表现；
4. 无法安全执行时，取消该动作，而不是伪造成功结果。

因此不安装模型也能游玩；模型用于增加角色感和变化，不是基础交互的单点依赖。

## 七、扩展玩法

新增玩法应优先组合现有角色、道具、关系和语义动作：

1. 在 `Resources/gameplay/` 声明玩法入口和可见信息；
2. 使用已有世界事件和场景节点描述开始条件、过程与成功结果；
3. 为缺少能力或素材的角色提供明确降级；
4. 用离线测试验证逻辑结果，再在真实桌面验证权限、布局和视觉表现。

公开仓库接受通用玩法代码和资源契约。角色美术、道具图片、内部训练数据、Harness、模型
评估和生产素材流程不属于公开仓库，通过正式 Release 提供可直接运行的完整内容。
